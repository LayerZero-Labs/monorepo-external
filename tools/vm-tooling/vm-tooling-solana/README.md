# @layerzerolabs/vm-tooling-solana

Solana tools for `lz-tool`: `anchor`, `solana`, `solana-verify`, and `surfpool`, each run in a Docker image.

## SBF stack-frame guard

platform-tools v1.53 and later print `Error: Function ... overflows the maximum allowed frame space` when a function needs more than the 4 KiB SBF stack frame, but `cargo build-sbf` still exits 0 and writes the program. A program like that can corrupt memory when it runs. The Solana image fails such a build, and no package script has to add anything.

- **Where.** `docker/solana/sbf-guard/cargo` is a bash wrapper. `docker/solana/Dockerfile` copies it to `/opt/sbf-guard/bin/cargo` and puts `/opt/sbf-guard/bin` first on the image `PATH`, before `/usr/local/cargo/bin` and `/usr/local/bin`. Only images built from this Dockerfile after the guard was added have it: `solana:anchor-1.2.1-solana-4.3.0-patch-1` and later tags. `lz-tool` does not set `PATH` in the container, so each `anchor` and `solana` run of such an image finds the wrapper, also with `--no-default-volumes`. `anchor build` starts `cargo build-sbf` through `PATH`, so a plain `anchor build` gets the guard, and so does a direct `cargo build-sbf`, also with cargo options before the command (`cargo +solana --locked build-sbf`, `cargo -C <dir> build-sbf`). The wrapper runs each other cargo command (`cargo build`, `cargo +nightly fmt`, `cargo metadata`) as the real cargo with the same arguments (`exec`).
- **Version gate.** The guard runs only for platform-tools v1.53 or later, v2.0 included. It reads `--tools-version` (`anchor build` 1.2.x always passes it, default `v1.57`). Without the flag, it reads the `platform-tools` line of `cargo build-sbf --version`. An older version runs the real `cargo build-sbf` unchanged. When the version cannot be found or parsed, the guard runs.
- **Check.** The wrapper copies the build output to the terminal unchanged (stdout and stderr stay separate) and searches both for `overflows the maximum allowed frame space`, whatever the exit code. Without that line, it exits with the build's code and changes nothing. With it, it prints `error: a function overflows its 4 KiB SBF stack frame ...`, deletes the program files (below), and exits 1, or with the build's own code when that is not 0.
- **Fail closed.** When the wrapper cannot capture or read the build output, it cannot check it, so it fails the same way: it prints `error: sbf-guard could not capture or read the build output ...`, deletes the program files, and exits 1 or with the build's own code. When it cannot set up the capture, the build does not run and the call exits 1: if `mktemp` fails, the wrapper prints only `mktemp`'s own error and deletes nothing; if `mkfifo` fails, it prints `mkfifo`'s error and the same `error: sbf-guard could not capture or read the build output ...` line, and deletes the program files.
- **Cleanup: which programs.** The wrapper deletes the `.so` of each program that the rejected `cargo build-sbf` call builds, and nothing else. It runs `cargo locate-project --message-format plain --offline` and `cargo metadata --no-deps --format-version 1 --offline` in the build directory, with the call's cargo options before `build-sbf` (such as `-C <dir>`) and its `--manifest-path`. The programs are the `cdylib` targets of the selected packages: the packages named by `-p`/`--package`, before or after `--`; else every workspace member, with `--workspace` or `--all`, before or after `--`; else the package whose manifest `cargo locate-project` finds (`--manifest-path`, else the nearest `Cargo.toml` in the build directory or a parent directory, as cargo finds it); else every workspace member, when that manifest is not a package (a virtual workspace manifest) or `cargo locate-project` fails. The file name is the lib target name with `-` replaced by `_`, plus `.so`.
- **Cleanup: which files.** The wrapper deletes that file in the output directory (`--sbf-out-dir`, else `SBF_OUT_PATH`, else `<target_directory>/deploy`; a relative path is relative to the build directory) and in the release directory of the SBF target (`<target_directory>/sbpf-solana-solana/release` for `--arch v0`, the default, and `<target_directory>/sbpfv<n>-solana-solana/release` for `--arch v<n>`). `<target_directory>` is the cargo argument `--target-dir <dir>` after `--` when the call has one (a relative path is relative to the build directory), else the `target_directory` of `cargo metadata`. `cargo build-sbf` does not read the form `--target-dir=<dir>`. It passes it on to cargo, which writes the release directory there, relative to the package directory (or to the workspace root, with `--workspace` or `--all` before `--`, or when the manifest is not a package or `cargo locate-project` fails, as above). So with that form, the wrapper takes the release directory from `<dir>`, and `<target_directory>` (for the default output directory) from `cargo metadata`, as the build does. Like the build, the wrapper resolves each of these paths, and the build directory, after following symlinks (physical paths), reads a value such as `-P` or `-` as a directory name, and ignores `CDPATH`. It prints `sbf-guard: deleted <path>` for each file that existed.
- **Cleanup: what stays.** IDL and types files, `.rlib` and `.d` files, and the copy in cargo's build directory (`release/deps`, which `lz-tool` keeps in its cache volume under `/cargo-target`). A later build of the same code fails again, because cargo replays the stored overflow line. When `cargo metadata` fails, the wrapper prints `sbf-guard: could not find the program files of this build (cargo metadata failed); deleted nothing` and still fails the build. When `jq` cannot read the `cargo metadata` output, it prints the same line with `(jq could not read the cargo metadata output)` instead, and still fails the build. When the output directory (as given, or after resolving symlinks, `.`, and `..`), the release directory (both as above), or the `--target-dir` value (as given, or after resolving) contains a newline, it prints the same line with `(a directory path contains a newline)` instead, and still fails the build.
- **`anchor build`.** It runs one `cargo build-sbf` per program and stops at the first rejected one. A program that it built earlier in the same `anchor build` passed the guard and keeps its `.so`.

Limits:

- `solana-verify build` builds in its own Docker container, which the guard does not see.
- A script that calls cargo by absolute path (`/usr/local/bin/cargo`, or `/usr/local/cargo/bin/cargo` in a run without the default cargo volume), or `cargo-build-sbf` directly, skips the guard. So does a run with `lz-tool --env PATH=...` that leaves out `/opt/sbf-guard/bin`.
- A multi-command `lz-tool --script` stops at a rejected build only when the script stops on a failure: `set -e`, or `&&` between commands. `lz-tool` runs scripts with `bash -c` and no `errexit`.
- `cargo build-sbf --debug` writes no `.so` in the output directory or the release directory. It writes `<output directory>/debug/<name>.so` and `<target_directory>/<sbf target>/debug/<name>.so` (for example `<target_directory>/sbpfv3-solana-solana/debug`), and the wrapper deletes neither. A rejected `--debug` build still fails, but both program files stay.
- Images built before the guard was added, and `lz-tool` runs that select them, have no guard.
- The wrapper runs the build as its child process, in the same process group, not with `exec`. When a signal ends only the wrapper process (for example `SIGTERM` from `kill <wrapper pid>`, or from `timeout --foreground`, which signals only the command it started), the wrapper exits without a check, and the build keeps running and can still write its `.so` afterwards. A `SIGINT` that reaches only the wrapper does not end it: it waits for the build and checks it. Ctrl-C in a terminal and `timeout` without `--foreground` signal the whole process group, so the build stops too. `docker stop` ends every process of the container when the container's main process ends.

Tests: `pnpm test:guard` proves the wrapper with a stub `cargo` (it also answers `cargo metadata` and `cargo locate-project`) and a stub `anchor`, without Docker or a Solana toolchain. The tests run the wrapper with `PATH` limited to the wrapper, the stubs, and `/usr/bin:/bin`, so they need `jq` in `/usr/bin` or `/bin` on the host; `jq` elsewhere on the host `PATH` is not found. `pnpm test` runs it after the Docker image tests.
