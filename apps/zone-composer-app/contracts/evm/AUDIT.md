# Zone composers — Audit Scope

## Files in Scope

- [`ZoneComposer.sol`](contracts/ZoneComposer.sol) and [`ZoneComposerNative.sol`](contracts/ZoneComposerNative.sol): ERC20 and native forwarding, authentication and rescue.
- [`IZoneComposer.sol`](contracts/interfaces/IZoneComposer.sol) and [`IZoneComposerNative.sol`](contracts/interfaces/IZoneComposerNative.sol): public interfaces.
- [`ZoneComposerMsgCodec.sol`](contracts/libs/ZoneComposerMsgCodec.sol): optional-memo encoding and decoding.
- [`IAirlock.sol`](../../../zone-router-app/contracts/evm/contracts/interfaces/IAirlock.sol): shared consumed Airlock functions and precompile address.

## Expected Usage and Trust

Each composer binds one OFT and its endpoint. They must authenticate delivery and credit the header's exact `amountLD` before compose execution. The ERC20 composer requires its router's token to match the OFT token; the native composer requires a native OFT, has `TOKEN == address(0)` and uses Airlock as `ROUTER`. Configuration is fixed. See [the composers](contracts).

For ERC20 forwarding, the configured router, token and optional burn/mint backend are trusted. They must settle exact amounts or revert; fee-on-transfer and rebasing tokens are unsupported. Backend permissions must allow the configured mode. Native forwarding relies on the native OFT credit and Airlock. The composer owner is trusted to choose local recipients for malformed credits and well-formed credits delivered while their router peer is absent or the native destination query returns false. See [`ZoneComposer`](contracts/ZoneComposer.sol), [router audit scope](../../../zone-router-app/contracts/evm/AUDIT.md) and [expected Airlock behaviour](../../../zone-router-app/contracts/evm/docs/expected-airlock-behaviour.md).

## Security-Relevant Mechanisms

- **Delivery and value.** `lzCompose` checks endpoint, OFT and zero attached value, then uses the OFT header's positive credited amount. Native `receive` accepts calls only from the OFT; forced native balances are not credited-message accounting. See [base](contracts/ZoneComposer.sol) and [native](contracts/ZoneComposerNative.sol).
- **Decoding.** Recipient offsets `0x40` and `0x60` select the two ABI forms. ABI decoding checks the selected tuple, without full canonical re-encoding: trailing bytes, noncanonical dynamic padding and overlapping tails can decode. A zero destination zone, an empty recipient, or a recipient or memo length over 255 reverts. See [the codec](contracts/libs/ZoneComposerMsgCodec.sol).
- **Failure boundary.** Decode failures create owner-rescuable GUID records. A missing ERC20 router peer or a false native zone query also creates a record, caches the transfer hash in `retryableMessages` and successfully consumes endpoint delivery. Anyone can `retry` that GUID with the `UnroutableZone` transfer; the router or `Airlock` rejects a destination that is still unroutable, and a failed retry reverts and keeps the record. Other forwarding reverts leave endpoint delivery retryable. Native query and send reverts remain endpoint-retryable. Native routing depends on the [Airlock interface assumptions](../../../zone-router-app/contracts/evm/docs/expected-airlock-behaviour.md#airlock-interface-assumptions). Successful forwarding, from `lzCompose` or `retry`, emits `Sent` with the GUID, destination zone and `Airlock` nonce, and creates no composer rescue record. See [`lzCompose`](contracts/ZoneComposer.sol) and [expected Airlock behaviour](../../../zone-router-app/contracts/evm/docs/expected-airlock-behaviour.md).
- **Rescue authority.** The composer owner can redirect a cached credit to any nonzero local recipient, including well-formed credits cached because routing was unavailable, until a retry succeeds. Rescue and a successful retry each clear both records, so only one of them settles a credit. Composer and router owners are independently configured and transferred. Clearing a router peer lets its owner make pending credits eligible for composer-owner rescue; any relayer can deliver them into that state. A rescue record is deleted before transfer and restored if transfer fails. Renouncing ownership is disabled. There is no general balance sweep or refund-to-source path. Both variants expose cached amounts through `rescuableMessages` and transfer hashes through `retryableMessages`. See [`retry` and `rescue`](contracts/ZoneComposer.sol) and [router peer configuration](../../../zone-router-app/contracts/evm/contracts/ZoneRouter.sol).
- **Allowances and dust.** The ERC20 composer grants maximum allowance to the router, or, in `BurnMint` mode, to a `burnerMinter` other than the token. The router debits the full credited amount. The native composer sends exactly the credited amount, independent of its other native balance. See [base](contracts/ZoneComposer.sol) and [native forwarding](contracts/ZoneComposerNative.sol).
