## Diff from the Audited Version

The audited version is [audit-external@596d9b2](https://github.com/LayerZero-Labs/audit-external/blob/596d9b2da3a9c3f02802c059af937e7ccb32c2e4/apps/multihop-composer-app/contracts/evm/contracts/MultiHopComposer.sol). It has diverged as follows.

1. **A set of OFTs on the hub chain replaces the two hardcoded `MESH_A_OFT` / `MESH_B_OFT` addresses.** E.g., the USDT0 composer is instantiated on Ethereum with the native mesh (`0x1F748c76dE468e9D11bd340fA9D5CBADf315dFB0`), the USDT0 mesh (`0x6C96dE32CEa08842dcc4058c14d3aaAD7Fa41dee`) and the USDT0 IOTA mesh (`0xAEf027F94008430BF4Fc27FFABB49ea6F1dd3414`). The contract needs to work in any topology combination: debit-credit mechanism (lock-unlock and burn-mint), number of meshes (1, 2, or many). Native OFTs (ETH) and alt chains are not supported.
2. **The compose payload changes from `SendParam` to `(SendParam sendParam, address oft, bytes32 refundTo, uint256 minMsgValue)`**, encoded by `MultiHopComposerMsgCodec`.
    1. `oft` selects the OFT the hop leaves the hub chain through.
    2. `refundTo` is where a refund goes back to on the source chain if the onward send reverts, falling back to the source sender when empty. This makes the composer safe to use behind other composers and wrapper contracts.
    3. `minMsgValue` closes a DoS vector where anyone can permissionlessly front-run the executor's `lzCompose` with `msg.value = 0` and then `refund` the failed hop. The attacker gains nothing, but the user loses their fees and is back to square one. `lzCompose` now reverts with `InsufficientMsgValue` below `minMsgValue`, so the compose is not consumed and can be delivered again with enough value. A `minMsgValue` of zero disables the check, and it only closes the vector when it is at least the expected fee of the onward send. The enforced minimum is capped at the owner-set `maxEnforcedMsgValue`, so a `minMsgValue` too high to pay cannot leave the compose undeliverable and its tokens stranded in the composer: it can always be delivered with the cap. The cap only keeps the vector closed for hops whose onward fee is within it, so the owner must keep it above the onward fees, and zero disables the check for every hop.
    4. `decode` rejects any payload whose first word is not the canonical `0x80` offset to `SendParam`. `abi.decode` accepts any in-bounds offset, so a legacy `abi.encode(SendParam)` payload would otherwise decode with its fields aliased as `oft`, `refundTo` and `minMsgValue`, and be refundable to the final recipient's address on the source chain.
3. **The contract is owned (`Ownable2Step`), and the owner recovers undecodable messages.** `refundTo` cannot help when the payload itself is malformed, so a user behind a composer or wrapper would still be exposed. A payload that fails to decode is now cached in `undecodableMessages`, and only the owner can release it on the hub chain through `rescue(guid, to)`. Previously it was stored as a `FailedMessage` and permissionlessly refunded to the source chain. Renouncing ownership is disabled (`CannotRenounceOwnership`), so undecodable messages always stay rescuable.

Other changes:

- `NATIVE_REFUND_RECIPIENT` is replaced by `nativeRefundRecipient`, which the owner can change through `setNativeRefundRecipient`, and which the constructor and the setter reject as zero (`InvalidNativeRefundRecipient`).
- The deliverer of a compose can no longer force a refundable failure through the native refund. The onward send refunds leftover native to `nativeRefundRecipient` instead of `tx.origin`, which can reject native under EIP-7702. A send that fails while the endpoint is already sending, i.e. a compose delivered from inside another endpoint `send`, reverts `lzCompose` instead of being recorded, so the compose stays queued for a normal delivery. Delivery itself stays permissionless: a deliverer can still pass any `msg.value` at or above `minMsgValue` capped at `maxEnforcedMsgValue`, so an enforced minimum below the onward fee lets it force a refundable failure, and it can consume shared state of the outbound OFT, such as a rate limit, before delivering.
- `ReentrancyGuard` is removed. `retry`, `refund` and `rescue` delete their record before making any external call. `lzCompose` has no guard of its own: the endpoint marks a compose as delivered before calling it, so the same compose cannot be delivered twice, and it rejects a nested `send`, so a compose delivered from inside a `send` reverts as described above.
- The internal hook `_lzCompose` is removed and its logic inlined in `lzCompose`. `_validateToken` and `_approveOFTs` are merged into the `virtual` constructor hook `_processOFTs`.
- `decodeSendParam` is renamed `decode`, `DecodeFailed` no longer carries the outbound OFT, and `FailedMessage` moved into the interface next to the new `UndecodableMessage`.
- The constructor rejects an empty OFT set and any zero or duplicate OFT with `InvalidOFT`.
- `send` is removed from `IMultiHopComposer`. It stays `public` on the contract behind `OnlySelf`, and now rejects an unregistered OFT with `InvalidOFT`, as `retry` does.
- `maxEnforcedMsgValue` is set in the constructor and by the owner through `setMaxEnforcedMsgValue`.
- New getters `TOKEN`, `isOFT`, `getOFTs`, `undecodableMessages` and `maxEnforcedMsgValue`, and new events `Rescued`, `NativeRefundRecipientSet` and `MaxEnforcedMsgValueSet`. `MESH_A_OFT`, `MESH_B_OFT` and `NATIVE_REFUND_RECIPIENT` are removed.
- `IMultiHopComposer.sol` moved to `contracts/interfaces/`, and the new `MultiHopComposerMsgCodec.sol` lives in `contracts/libs/`.

## Security-Relevant Mechanisms

- **Access control.** `lzCompose` accepts calls only from the endpoint the OFTs are registered with, and only when the composing OFT is registered. The payload chooses the outbound OFT, so `send` and `retry` reject any OFT that is not registered with `InvalidOFT`; a record naming an unregistered OFT can only be refunded through the inbound OFT. `send` is externally exposed but reverts with `OnlySelf` unless the caller is this contract; `lzCompose` reaches it through an external self-call so that a failing send can be caught rather than reverting the whole compose. `rescue`, `setNativeRefundRecipient` and `setMaxEnforcedMsgValue` are owner-only.
- **The onward amount is taken from the compose header, not the payload.** A payload requesting more than arrived would otherwise reach tokens left in this contract by earlier failed hops. This override is the invariant that keeps those balances out of reach. It assumes the token credits the composer exactly the header's `amountLD`, i.e. it takes no fee on transfer and does not rebase. Ethereum USDT has a fee switch (`basisPointsRate`, `maximumFee`) that is currently off; if it were turned on, the composer would receive less than `amountLD` while the onward send still pulls the full amount, drawing the difference from other hops' balances.
- **No slippage protection.** The onward send is forced to `minAmountLD = 0`, so the recipient accepts whatever survives both OFTs' fees. LayerZero hops do not convert tokens, so the only deltas are each OFT's own fee.
- **Failure handling.** There are three failure scenarios:
    1. The payload fails to decode. The hop is cached in `undecodableMessages` and only the owner can `rescue` it.
    2. `msg.value` is below the payload's `minMsgValue`, capped at `maxEnforcedMsgValue`. `lzCompose` reverts, and the compose can be delivered again with enough value.
    3. The onward send fails. The hop is recorded in `failedMessages` and can be permissionlessly retried or refunded, unless the endpoint is mid-send, in which case `lzCompose` reverts as in 2.

    A compose that runs out of gas before recording anything reverts entirely and is recoverable only by delivering it again. The revert data of a failed decode or send is not emitted, so the cause of a failure has to be determined off-chain.

- **A send that runs out of gas can still be recorded (acknowledged).** `lzCompose` is permissionless, so the deliverer picks its gas. Each call forwards at most 63/64 of the gas left (EIP-150), so when the outbound OFT's `send` runs out of gas k calls below `lzCompose`, about 1 - (63/64)^k of the gas comes back to it. If that covers recording the failure, about 225k gas, a send that would succeed with more gas is recorded instead, and anyone can then `refund` it. The composer does not guard against this, as it needs a far heavier send than today's: on the USDT0, PYUSD0, USDG0 and AUSD0 hubs, `send` costs about 300k–405k gas and no delivery gas forces a recorded failure, while it takes a single call needing about 7M gas in `send` itself, or about 1.3M gas 10 calls below `lzCompose`, the depth of the deepest call in today's sends.
- **Refund routing.** Refunds go to the payload's `refundTo`, or to the source sender when it is empty. If that address is not user-controlled on the source chain, such as a wrapper contract or another composer, refunded funds can be permanently lost.
- **Recovery callers cannot add options.** `retry` resends the recorded `SendParam` with the options from the original payload, and `refund` sends with empty `extraOptions`; neither takes options from its caller, because the cached native value could otherwise be drained through a native drop addressed elsewhere. Leftover native value goes to `nativeRefundRecipient` on the onward send and on a refund, including any value the refund caller added, and to `tx.origin` on a retry.
- **The native refund recipient must accept native.** `refund` names `nativeRefundRecipient` as the refund address for the messaging fee: the endpoint sends it whatever part of `msg.value` plus the cached compose value the refund's fee does not use, and reverts the whole refund with `Transfer_NativeFailed` if that transfer fails. The cached value was paid for the onward hop to the destination chain rather than for the return to the source chain. While the recipient rejects native, any hop whose cached value exceeds its refund fee cannot be refunded until the owner replaces the recipient.
- **Refunds rely entirely on enforced options.** A refund carries empty `extraOptions`, so the inbound OFT must provide enough enforced options for destination execution; without them the refund reverts. Second hops, including retries, instead use the options encoded in the nested `SendParam` combined with the outbound OFT's enforced options. The inbound compose also needs enough `lzCompose` gas from the source message's user or enforced options.
- **Every registered OFT holds an unlimited allowance.** Each OFT is approved for `type(uint256).max` without relying on its `approvalRequired()` response. A hop may debit the outbound OFT while a refund may debit the inbound OFT, and all registered OFTs are trusted. Tokens stranded by failed hops therefore sit in a contract that any registered OFT can pull from.
- **Shared decimals are not checked.** The constructor does not require the registered OFTs to agree on `sharedDecimals()`. When the inbound and outbound OFTs differ, the outbound OFT drops the dust below its own conversion rate on every hop, and that dust stays in this contract with no record, so neither `retry`, `refund` nor `rescue` can recover it.
- **Non-compliant underlying tokens.** Approvals use `SafeERC20.forceApprove` rather than `IERC20.approve`, since a token such as Ethereum USDT returns no value from `approve` and would revert the compiler's return-value decode.
